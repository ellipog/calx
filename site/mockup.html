Parallel loops

Every core, and the same answer every time

parallel for runs a loop's iterations across a pool of threads. The checker makes sure no iteration touches what another one changes, so the program prints the same thing on one thread or twenty-four.

  • The check is the ownership check, applied between iterations. It costs nothing at run time.
  • What iterations print comes out in their order, and a panic reports the first iteration that panicked.
  • Calx compiles to C. The C tab shows what this loop becomes: a function per chunk, its pointers marked restrict.

Reference/Parallel loops

Parallel loops

parallel for, the capture check that keeps iterations apart, why results don't depend on the thread count, and its C.

All 6 examples compiled and run by CI at 35824ea Edit this page

parallel for runs a loop's iterations at once, on a pool of threads. It's the only parallelism in Calx D21, and the checker makes sure the iterations can't touch the same memory, so a program gives the same result with one thread or with many.

The loop goes over a range of integers, as a for loop can. Each iteration gets its own value of the loop variable, here k, and the loop returns once every iteration has finished.

Over the elements#

A parallel for can also go over the elements of a list or an array. With mut, each iteration gets a view of its own element and changes it, as a for x in mut xs loop does D116:

Nothing in the body reaches the list except through the element, so no iteration can reach another's. Without mut, each iteration reads its element, and the body can read the list as well, since no iteration changes it.

What an iteration can touch#

An iteration changes only its own elements: places it reaches by indexing with the loop variable itself, such as regions[k] or world.states[k].entities. No other iteration has the same k, so no other iteration can reach them. It can read anything that no iteration changes.

In the bodyAllowed?
Change xs[k], or any part of itYes
Change x, or any part of it, in parallel for x in mut xsYes
Use xs itself in parallel for x in mut xsNo: only through x
Change w.blocks[k] and w.states[k] in one iterationYes: separate fields are separate values
Read xs.len() while iterations change elements of xsYes: changing an element doesn't change the length
Change a variable from outside, such as total += 1No: every iteration would change it at once
Change xs[k + 1], xs[j] or xs[0]No: another iteration might reach the same element
xs.push(x) on a list from outsideNo: that changes the list itself

Calls count too. Passing mut regions[k] to a function lets it change that element and nothing else, and passing w.blocks lets it read them. The check is the same one that keeps a mut argument apart from the other arguments of a call, applied between iterations.

Control flow#

continue ends one iteration early. break and return aren't allowed in the body, since every iteration runs. A break or return inside a loop or function in the body is fine.

Loops inside loops#

A parallel for can run inside another, even through a function the outer one calls, as a region running a loop of its own. A thread that has nothing left of the outer loop to take helps the inner loops instead, so a world with one busy region still gets every thread.

The same result with any number of threads#

Iterations can't see each other's changes, so what each computes doesn't depend on which thread ran it or when. Two more things make the whole program's behavior the same with one thread and with many:

  • Output comes out in order. What an iteration prints is held until the loop ends, then written in the order of the iterations.
  • A panic reports the first iteration that panicked, with the output of every iteration before it, and exits with status 101, as running them in order would.

In C#

The body becomes a C function of its own, which the runtime calls for each chunk of the range. Everything it reaches from outside is a pointer that the function declares restrict, since the checker made sure no iteration reaches what another changes, so clang optimizes the body as it would a function's. The C tab on the first example shows it.
